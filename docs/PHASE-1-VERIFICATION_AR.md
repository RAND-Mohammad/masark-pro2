# مسارك — سجل المرحلة الأولى

تاريخ الفحص: 2026-10-15. النطاق: الحسابات وتأكيد البريد والاستعادة والجلسات والمزامنة وعزل بيانات الحساب فقط.

## ما ثبت وما لم يثبت

| العنصر | الدليل | حدود النتيجة |
| --- | --- | --- |
| إعداد مصادقة Supabase | `GET /auth/v1/settings`: HTTP 200؛ البريد مفعّل، التسجيل مسموح، تأكيد البريد مطلوب | ليس اختبار إنشاء حساب أو تسليم رسالة جديدة |
| الوصول كضيف إلى بيانات الحساب | `GET /rest/v1/masarak_account_data?select=user_id&limit=0`: HTTP 401، الرمز `42501`، دون قراءة صفوف | رفض طلب ضيف فقط؛ لا يثبت صحة جميع السياسات أو عزل حسابين |
| وصول دالة البريد | POST غير موقّع بجسم `{}`: HTTP 401 ورسالة رفض توقيع الدالة نفسها | ليس خطأ 503 أو رفض JWT من البوابة؛ لا يثبت كامل إعداد مزود البريد بهذا الطلب وحده |
| التوقيع والإرسال | اختبارات التوقيع والإرسال السابقة ناجحة، ووصول رسالة الاختبار أكّده المستخدم | دليل سابق؛ لم تُرسل رسالة أخرى في هذه المرحلة، ولم تُفحص رحلة Auth حقيقية بعد تفعيل Hook |
| المرسل | ضبط الاسم سابقًا إلى «مسارك \| Masarak» مع إبقاء هوية المرسل | لم يجر تعديل جديد للمرسل أو مصادقته |
| روابط العودة المحلية | قائمة السماح موجودة وتشمل عنوان معاينة الويب الحالي و`masarak://auth-callback` | `masarak:///auth-callback` غير موجود في القائمة؛ يجب مطابقة الرابط الذي ينتجه بناء الجوال فعليًا قبل اعتماده |
| Hook | تحديث مؤكد من المستخدم: تم تفعيله في اللوحة وظهر Enabled | لم يفعله الوكيل، ولا يوجد وصول إداري مستقل لقراءة مفتاح التفعيل |
| سياسات الحساب وصلاحيات الأدوار | أكد المستخدم من SQL سياسات العمليات الأربع `auth.uid()=user_id`؛ authenticated الأربع true وanon الأربع false | دليل من اللوحة، لا اختبار مستقل لحسابين أو دليل على بقية إعدادات RPC وStorage |

لم تُقرأ مفاتيح Supabase الإدارية أو بيانات حسابات المستخدمين. لا توجد وسيلة SQL إدارية متاحة للوكيل؛ نتائج السياسات المذكورة أعلاه نقلها المستخدم من اللوحة، ولم يُختبر حفظ حسابين حقيقيين من هنا.

## التعديلات المحلية

1. شاشة الاستعادة مشتقة من الجلسة الحالية؛ وصول الجلسة أثناء فتح الشاشة ينقلها إلى تغيير كلمة المرور، وفقدها يزيل النموذج.
2. رسالة الاستعادة رابط أولًا؛ إدخال الرمز احتياطي اختياري، مع دعم الأرقام العربية.
3. مؤقت محلي لإعادة الإرسال 60 ثانية وقفل للنقرات المتزامنة. هذا تحسين للواجهة ولا يغني عن حدود Supabase والخادم.
4. لا نجاح دخول دون جلسة، ولا نجاح تأكيد رمز دون جلسة، ولا نجاح تغيير كلمة المرور دون مستخدم مطابق للحساب.
5. حدث `PASSWORD_RECOVERY` ومسار الدخول يحافظان على توجيه الاستعادة بدل الانتقال للصفحة الرئيسية.
6. تنظيف معاملات ورموز رابط التأكيد من عنوان المتصفح حتى عند الرابط الناقص/المنتهي، دون تسجيلها.
7. عملاء نقل المزامنة المؤقتون لهم نطاقات تخزين Auth منفصلة ولا يحفظون جلسة ثانية؛ الطلب يبقى مربوطًا برمز صاحبه الأصلي.

## ما راجعناه في المزامنة

- بيانات الضيف وكل حساب منفصلة محليًا، ولا تُرفع بيانات الضيف تلقائيًا إلى حساب جديد.
- تفعيل الحفظ السحابي اختياري؛ الإيقاف يمنع الطلبات، واسترجاع جهاز جديد وتعارض البيانات لهما مساران صريحان.
- نسخة `revision` وRPC تمنعان الكتابة القديمة؛ تعديلات أثناء التحضير/الرفع تبقى معلقة للمحاولة التالية.
- تبديل الحساب يوقف العملية ويلغي نطاقها؛ ملفات السيرة مرتبطة بمجلد صاحبها ومخزن خاص في مخطط SQL المحلي.
- اختبارات الكود تحاكي أخطاء الشبكة وتعارض الأجهزة وتبديل الحساب وفشل الاسترجاع وإرجاع الكتابات المحلية.

هذه أدلة تنفيذ واختبارات محاكاة، لا دليل تشغيل حي لقاعدة البيانات أو اختبار جهازين.

## فحص RLS الحي دون تغيير أي صلاحيات

افتح SQL Editor في مشروع Supabase الصحيح وشغّل الملف:

`supabase/003_audit_account_cloud_readonly.sql`

الملف ينفذ معاملة `READ ONLY` وقراءة كتالوج فقط؛ لا يستدعي الحفظ ولا يكتب بيانات ولا يبدل الأدوار.

المطلوب مراجعته:

- الجدول موجود و`rls_enabled=true`؛ صلاحيات `anon` الأربع `false`، وصلاحيات `authenticated` المطلوبة متاحة مع RLS.
- سياسات الحساب: SELECT/INSERT/UPDATE/DELETE للمستخدم المسجل، بشرط `auth.uid() = user_id`؛ التحديث له USING وWITH CHECK. لا سياسة عامة إضافية تفتح الوصول.
- RPC موجود، `is_security_definer=false`، و`search_path` محصور؛ `anon_can_execute=false`، و`authenticated_can_execute=true`.
- مخزن `masarak-cvs` موجود و`public=false`، وحدود الحجم والأنواع مطابقة للمخطط المحلي.
- سياسات الملفات تربط المجلد بالمستخدم والمخزن، ولا سياسة Storage عامة تتجاوزها.
- `force_rls=false` وحده ليس إثبات خلل: أدوار التطبيق لا ينبغي أن تكون مالكة للجدول أو تحمل BYPASSRLS.

الملف الأقدم `002_verify_account_cloud.sql` **ليس قراءة فقط**: ينفذ كتابات اختبارية على حساب موجود ثم يتراجع عنها بـROLLBACK. لم يُشغّل هنا، ولا يُشغّل باعتباره فحصًا بلا كتابة. اختبار A/B الحقيقي أو هذا الاختبار المؤقت يحتاجان موافقة وبيئة مناسبة.

## أقل خطوات لفحص وتفعيل Send Email Hook من اللوحة

**تحديث:** فعّل المالك Hook وظهر Enabled. لا تعِد إنشاء Hook أو توليد السر؛ الخطوات التالية مرجع للإعداد الذي تم، وليست طلبًا لتكراره.

لا يلزم نشر تطبيق مسارك أو تغيير RLS أو تعطيل تأكيد البريد.

1. **فحص فقط:** Edge Functions → `send-auth-email`. تأكد من الدالة الحالية والأسرار/الإعدادات الأربعة: `BREVO_API_KEY` و`SEND_EMAIL_HOOK_SECRET` و`EMAIL_HOOK_SENDER_ID` و`EMAIL_HOOK_REDIRECT_URLS`. لا تولّد مفتاحًا جديدًا ولا تعرض القيم في محادثة أو سجلات.
2. فحص Settings للدالة: توقيع Hook هو التحقق المطلوب؛ إعداد Verify JWT القديم لا ينبغي أن يمنع طلب Supabase Auth. الطلب السابق وصل فعلًا لمدقق التوقيع. لا تغيّر هذا المفتاح مرة أخرى إن كان مضبوطًا.
3. Authentication → URL Configuration: طابق روابط العودة المسموح بها مع القائمة التي تستخدمها الدالة. افحص الناتج الفعلي على بناء الجوال؛ روابط Expo Go أو اختلاف الشرطتين/الثلاث ليست دليلًا على صلاحية رابط بناء مستقل. لا تضف wildcard عامًا.
4. Authentication → Hooks → Send Email: اختر HTTPS، والعنوان:

   `https://fhpumqlsepbprfimxaon.supabase.co/functions/v1/send-auth-email`

5. خانة Secret يجب أن تطابق **القيمة الموجودة** في `SEND_EMAIL_HOOK_SECRET` داخل Supabase. إذا كانت محفوظة فلا تعِد توليدها. توليد قيمة مختلفة يكسر التوقيع؛ توقف وطابق الإعدادات عبر الحقول الآمنة إذا كان هناك شك.
6. بعد تحقق المالك من ذلك يضغط **Create hook / Save** مع التفعيل. هذا تفعيل خدمة بريد Auth فقط، وليس نشر التطبيق. سيستبدل إرسال البريد الافتراضي لكل إجراءات Auth التي تصل للدالة.
7. بعدها، وببريد تجريبي مأذون به، تُختبر رحلة التطبيق الحقيقية: تسجيل جديد ورمز 6 أرقام، خطأ/انتهاء/إعادة إرسال، دخول بكلمة المرور، ثم طلب رابط استعادة واستعماله مرة واحدة وتغيير كلمة المرور والدخول بها. اختبارات التوقيع السابقة لا تحل محل هذه الرحلة.
8. راقب HTTP وملخص الأخطاء ومعرف الرسالة فقط؛ لا تسجل جسم Hook أو رمز البريد أو رموز الجلسة. `401` من الدالة يعني فشل التوقيع، و`503` قد يعني نقص الإعداد/تعطل خدمة؛ لا تعالج ذلك بتعطيل حماية التوقيع أو تأكيد البريد. عند فشل التفعيل، يوقف المالك Hook مؤقتًا ويشخّص السبب.

**ما نفّذه هذا الفحص خارجيًا:** طلبات قراءة إعدادات/رفض ضيف وطلب دالة بلا توقيع وبلا مستلم فقط. لا بريد جديد ولا تفعيل Hook ولا تعديل صلاحيات ولا حذف بيانات ولا نشر.

## الاختبارات ومعيار إغلاق المرحلة

أوامر التحقق المحلية:

```sh
node --test tests/*.test.cjs tests/*.test.mjs
npm run test:cv-server
npm run lint
npx tsc --noEmit
```

الاختبارات الجديدة تشغل handlers وeffects الفعلية مع جلسات ومزوّد محاكيين؛ لا تنشئ حسابات ولا ترسل بريدًا. الاختبارات لا تثبت تشغيل iOS/Android ولا صحة إعدادات مشروع Supabase المرفوع.

### نتيجة التحقق المحلي

- اختبارات التطبيق وHook: **111 ناجحًا، صفر فشل**.
- اختبارات الخادم: **42 ناجحًا، صفر فشل**.
- `expo lint` و`tsc --noEmit`: ناجحان دون أخطاء.
- أُعيد تشغيل معاينة مسارك؛ السجل نظيف وشاشة طلب الاستعادة ظهرت صحيحة بعرض 402×874 في متصفح غير مسجل.
- لم تُفحص واجهة مسجل الدخول بصريًا ولم يُشغّل بناء iOS أو Android. صورة المتصفح ذات عرض الهاتف ليست اختبار جهاز أصلي.

يبقى إغلاق المرحلة مشروطًا بما لم يُتحقق منه في SQL وفحص حسابين/جهازين، وتجربة رحلة Auth الحقيقية بعد التفعيل، واختبار بناء iOS وAndroid. الواجهة المسجلة بالدخول لا يمكن فحصها بصريًا بمتصفح الالتقاط غير المسجل. توقف العمل الحالي بعد إصلاح الاستعادة واختباراته؛ تشخيص فتح الجوال مهمة لاحقة مستقلة.
